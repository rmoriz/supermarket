# supermarket-rs — production-compatible Rust port: design

**Date:** 2026-11-16
**Status:** draft
**Reference (read-only):** `supermarket-ruby/` @ `80d517b2`

## Intent

Replace the Rails application at `supermarket-ruby/src/supermarket` with a Rust
service that is a **drop-in production replacement**: the same URLs, the same
wire formats, the same database, the same OAuth providers, the same background
work — deployed for the existing public instance, with a rollback path.

"Compatible" here is measured on the wire, not by feature resemblance:

- The same method+path returns the same status code, the same body bytes (modulo
  normalization below), and the same semantically relevant headers.
- The same auth works: `mixlib-authentication` signed API uploads against the
  user's stored public key, Rails-encrypted session cookies, Chef oc-id and
  GitHub OAuth logins.
- Existing clients (`knife supermarket`, Berkshelf `supermarket` source, the
  `chef` CLI) need no changes.
- The existing database and S3 bucket work unchanged; no migration is required
  to switch over.

## Why this is feasible now

- The surface is enumerable: `config/routes.rb` (144 lines, 25 tables) plus one
  vendored engine (`fieri`) — all in-tree as the contract.
- The RSpec suite (159 files) documents intended behaviour per endpoint, and the
  app can be run locally, so the Rails process itself is the oracle.
- Where the port touches storage, the Rails app is thin over Postgres: most
  endpoints are a query plus a jbuilder template.

## Goals

- Wire-identical behaviour for every route in `config/routes.rb`, including HTML
  pages and error envelopes.
- Same Postgres schema, same data; zero downtime cutover, instant rollback.
- Ported `mixlib-authentication` verification with byte-level test vectors
  generated by the Ruby implementation.
- Background jobs, mailers, cache keys, statsd metric names and feature-flag
  semantics carried over so Rails and Rust can run side by side.
- Every ported behaviour pinned by a differential test that compares Rust to a
  live Rails instance on seeded data.

## Non-goals

- No new product features, no UI redesign, no API version bump.
- No schema redesign or ORM. ActiveRecord stays the schema owner until cutover;
  Rust issues SQL against the same tables.
- No `rspec`/Ruby in production; Ruby is a build-time and staging-time oracle
  only.
- Not porting upstream's dead surface (`docs-chef-io`, omnibus/habitat packaging,
  dev-vm scripts).

## Anti-goals

- A port that passes the happy-path specs but drifts on error bodies, redirects
  or ordering. Ordering and error text are part of the contract.
- "Improving" the HTML so selectors and JS break.
- A big-bang cutover with no dual-run window.

## Constraints

- **Schema frozen.** No migrations, no column additions, no index changes during
  the port. `int` primary keys, `precision: nil` timestamps, `json` columns
  (`chef_versions`, `ohai_versions`), `roles_mask`/`badges_mask` bitmasks,
  `pg_trgm` extension, unique indexes all stay exactly as `db/schema.rb` has them.
- **Sessions shared.** Rails cookies are AES-256-GCM authenticated-encrypted with
  `secret_key_base`, JSON serializer, cookie name from
  `config/initializers/session_store.rb`. Rust must read and write that exact
  format, or users are logged out on every flip.
- **Auth is three schemes, kept distinct:** session cookie (web), mixlib
  signature (API writes), OAuth (login only). The signature verifier must accept
  the protocol levels the Ruby client sends and reject the same things it
  rejects.
- **Error envelope is i18n.** Port `config/locales/*.yml` strings verbatim; API
  errors are `{"error_code":…,"error_messages":[…]}` with the same codes and
  statuses (`invalid_data`, `not_found`, `unauthorized`, `forbidden`,
  `authentication_failed`).
- **Secrets by the same env var names** (`SECRET_KEY_BASE`, `S3_*`, `REDIS_URL`,
  `DATABASE_URL`, `CHEF_OAUTH2_*`, `GITHUB_*`, `FIERI_URL`, `API_ITEM_LIMIT`,
  `FQDN`, `PORT`).
- **Copy drops the word "Chef" wherever the sentence survives** (see *Copy and
  naming*), which makes HTML a deliberate non-byte-match.
- **Paperclip-compatible storage layout** in S3 and on disk (path prefix,
  `tarball_file_name`, `tarball_updated_at`); downloads redirect to
  `cookbook_artifact_url` exactly as today, honouring `S3_URLS_EXPIRE`.

## Approach

Parity-first, API first, with a differential oracle (chosen over UI-first and
over a proxy-first strangler; the strangler is used only for the final rollout,
not for development).

Order of work follows blast radius, not ease: the machine surface that breaks
clients first, the human UI after, admin/CLA last.

### Architecture

One binary, one router mirroring `routes.rb` route-for-route (including the
legacy `/api/v1/universe`, `/status`, `/robots.txt`, atom feeds and the
`fieri` mount under a flag):

- **HTTP** `axum` + `tower` (limits, timeouts, compression, rate limits).
- **DB** `sqlx` (Postgres) with compile-time checked queries; one pool, same
  transaction boundaries as the ActiveRecord callbacks it replaces.
- **Templates** `askama`, ported from ERB, with the same partial decomposition
  and `data-*` hooks.
- **Search** hand-written SQL reproducing exactly what `pg_search` emits for
  `Cookbook.search` (A-weighted trigram on name, B on username, C on
  description, `ranked_by`, `order_within_rank`).
- **Cache/queues** Redis: `UniverseCache` keys (`http-universe`, `https-universe`),
  Rails.cache semantics, and Sidekiq-compatible JSON jobs on the same queues.
- **Jobs** Rust workers consuming those queues; while any Rails worker remains,
  it can keep consuming (same payload shape, same args).
- **Mail** `lettre` + templates ported from the mailers, same subjects/bodies,
  `EmailPreference` unsubscribe tokens, `SystemEmail` rows.
- **Storage** `aws-sdk-s3` and local filesystem behind one trait.
- **Observability** `tracing`, statsd metric names unchanged
  (`cookbook.downloads.api`, `cookbook.version.published`, …), Sentry
  `sentry`-compatible DSN, `/api/v1/health` and `/api/v1/metrics` parity.

### Differential harness

`harness/` (Ruby, build-time only):

1. Boots Postgres+Redis, loads `db/schema.rb`, seeds via `db/seeds.rb` plus
   RSpec factories to reach the states specs rely on.
2. Boots the Rails app on `:3001` and the Rust binary on `:3002` against
   **separate databases with identical content**, same `secret_key_base` and
   same clock.
3. Replays a corpus of recorded requests (captured from the RSpec suite plus
   hand-built edge cases: missing params, wrong verbs, unknown users, negative
   `start`/`items`, oversize uploads, bad signatures, deprecation/`latest`/
   `_`-version forms) against both, and diffs.
4. Normalizes only: timestamps, autoincrement ids, CSRF tokens, ETags, S3
   signed-URL parameters, `Set-Cookie` value, the copy map from
   `docs/copy-changes.md` applied to the Rails side, and attribute
   order-insensitive comparison for page bodies. Everything else must match
   byte-for-byte.

Rule: a route is ported only when its corpus is green. A bare `501` stub keeps
the router complete from day one, so the harness can measure progress route by
route.

## Phases (each ends with a green corpus for that slice)

0. **Skeleton + harness.** Cargo workspace, config from env, DB pool, cookie
   crypto, error envelope, `501` stubs for every route, harness running, CI.
1. **Public read API.** `/universe` (SQL + Redis cache + `hits`), search,
   cookbook index/show/contingent, version show/download with counters and
   redirects, users show, metrics/health, tools.
2. **Uploads and API auth.** Signature verification (vectors from Ruby),
   multipart parsing, tarball/gzip + `metadata.json` validation, category
   resolution, dependency/platform import, ownership rules, unshare,
   version delete, SPDX worker hand-off.
3. **Web UI, read paths.** Layout, CSS/JS assets served as today, welcome,
   directory with filters/sort/pagination, cookbook and version pages, user and
   group pages, search.
4. **Web UI, mutations.** Follow/unfollow, deprecate/undeprecate, adoption,
   featured toggle, ownership transfer requests, collaborators, profile.
5. **Identity, CLAs, admin.** oc-id/GitHub login and linking, account unlink,
   organizations, contributor requests, invitations, ICLA/CCLA signatures,
   role/admin actions, email preferences.
6. **Background work.** Cookbook notify/deletion/deprecation mailers, OAuth
   token refresh, sitemap refresh, SPDX licence fetch, sidekiq-cron schedule.
7. **Remaining surfaces.** Fieri engine and quality metrics, chat/IRC logs,
   tools directory, robots, atom feeds.
8. **Cutover.** Strangler proxy in front of Rails, group-by-group flip with
   shadow reads on `universe`/search, then write cutover in a short
   maintenance window, then proxy removal.

## Cutover, rollback

- Route groups flip in the reverse of blast radius (chat/tools/feeds → UI →
  reads → uploads last), each behind a proxy switch; every flip is reverted by a
  config change, no deploy.
- `universe` and search run shadowed (Rust answers discarded) and are diffed in
  production before being served.
- Upload cutover happens in a short window with Rails write handling stopped; if
  the corpus or error budget regresses, flip back — the schema never diverged,
  so rollback is lossless.
- Rust never deletes S3 objects for the first 30 days after cutover.

## Copy and naming

The port never says the word **Chef** in a resource a human reads, unless leaving
it out breaks the meaning or the wire format. That covers page copy, `<title>`,
meta descriptions, headings, buttons, flash messages, error pages, mailer
subjects and bodies, feed titles, and `alt`/`title` attributes.

- Write "Supermarket", "the community site", "your account", "a cookbook
  maintainer", "Infra Client"/"Infra Server". `<title>` becomes
  `Page - Supermarket`; the mailer layout title becomes `Supermarket`.
- Product names lose the brand where the noun still carries it: "Required Chef
  Infra Client" → "Required Infra Client"; "this Supermarket's Chef Server" →
  "this Supermarket's server".
- **Keep, because the wire or an external system requires it:** API JSON keys and
  values (`chef_versions`, `ohai_versions`, `location_type: "opscode"`), the
  `chef_oauth2` provider identifier, `X-Ops-*` headers, `metadata.json` fields,
  cookbook readmes/descriptions (author content), database columns, env vars, and
  URLs on `chef.io`/`status.chef.io`/`discourse.chef.io` plus link text that names
  those sites.
- Every changed string is listed in `docs/copy-changes.md` (file, before, after,
  reason). That file is the review surface for the rewrite's voice, and the
  harness applies it to the Rails output before diffing, so copy changes stay
  deliberate instead of becoming diff noise.

Not renamed, to keep clients working: routes, query parameters, JSON keys, cookie
names, uploaded-artifact paths.

## Security

Same controls, explicitly ported: CSRF tokens (`X-Ops-CSRF-Token`-independent,
double-submit + authenticity token; API exempt), signed/encrypted cookies,
`safe_constantize`-style lookup, strong-params-style allow-lists, IO limits
(tarball size, decompressed size, entry count, `metadata.json` required),
timestamp skew window and canonical-path checks in signature verification,
`allow_other_host` redirect semantics, same-content-type tarball allow-list,
S3 URL expiry.

## Observability and operations

`/api/v1/health` checks DB, Redis and S3 as today; `/api/v1/metrics` returns the
same shape. Same statsd names, same Sentry tags. Dashboards keep working by
name. Feature flags (`Feature.active?` rollout semantics, `fieri`, `tools`) read
the same Redis-backed store.

## Testing

- Differential corpus per route (above) — the primary gate.
- Ported RSpec feature specs run against the Rust host via Capybara remote, so
  the human-facing behaviour keeps its original assertions.
- Property tests for signature canonicalization/cookie crypto against Ruby
  vectors, including negative cases.
- Load tests on `universe`, search and download before their flip.

## What is left to the builder

Crate choice details below `axum`/`sqlx`/`askama`, module layout, harness
transport, seed staging, the exact per-route corpus contents, and the copy
inventory in `docs/copy-changes.md` (which strings change and to what).

## Risks

| Risk | Mitigation |
|------|------------|
| Cookie crypto mismatch logs everyone out | Port against Ruby vectors in phase 0; dual-read check before any flip |
| Signature verification drift breaks `knife` | Vectors from `mixlib-authentication` incl. rejection cases; corpus replay against real `knife` |
| `pg_search` ranking differs subtly | Compare result *order and score* against Rails on production-shaped data; never "improve" the SQL |
| HTML drift breaks JS/selectors | Askama port of partials + DOM assertions from feature specs, not string equality of the whole page |
| Upload path edge cases corrupt data | Full `CookbookUpload` transaction port, plus the spec's failure matrix in the corpus |
| Sidekiq payload drift strands jobs | Same JSON shape and queue names, verified by a Ruby consumer in staging |
